## Summary

Two halves in one PR:
- **Measurement:** `/review-loop` records measured per-phase wall-clock (review, autofix, CI wait), escalation wait, and where each re-review finding sits relative to the previous iteration's fix diff. `report.py` gets a review-loop cost view.
- **Fix quality:** `/autofix` hardens behaviour-changing (RISKY) fixes with a blast-radius check, a rule stated before the fix, and a regression test. `autofix_applied` counts how many of those fixes got a test.

Iteration decisions don't change.

**Escalation state**
- `review_iteration` events have `ts` (end of iteration), `pr`, `iter`, `action=escalated`, and `project` (the worktree basename).

- Joining events across worktrees is unreliable: `session_id` is always null and PR numbers collide across repos.

### Constraints / dependencies
- Keep the "iteration decisions don't change" contract. New envelope fields are measurement only.
- New `*_s` fields need a ≥0 rule, since `INT` allows negatives.
- `INT` is global, so a new field name must not clash with an existing field's meaning in another event.
- On phases that didn't run, omit the field; never emit 0.
- Classification needs the previous iteration's `pre_sha`, `post_sha` and `findings_summary`, carried into the next worker prompt in-process. A cold resume has none of these, so classification is omitted there.
- Most risky fixes in hivesmith itself are SKILL.md prose, where no executable regression test is possible.
- Risky fixes inside a review-loop worker escalate (no AskUserQuestion in a sub-agent), so hardened fixes mostly happen on operator-attended runs.

### Prior lessons
- **Fixes are the riskiest code in a PR** (`review-fixes-need-their-own-review-pass`). The fixes applied between iterations are the most defect-dense code in the PR: each fix broke a neighbouring invariant until the worker was told to re-derive the prior fix independently. This supports the near-fix-diff classification and the "state the rule first" step.
- **Check doc claims against the tree** (`verify-doc-claims-against-tree`). Grep every claim in the changeset and doc prose against the tree. Tests written in the same commit are not evidence.
- **Negated assertions can be inert** (`inert-negated-assertions-under-errexit`). Under `set -e`, a negated assertion (`! cmd`) never fails the script. Watch for this in new test assertions that use `!`.

## Approach

This is one PR in three layers. Every new metric is **optional** and **measured**. Every new review-loop step is **measurement only**: the §2 step 5 decision rules and the §2.3/§2.5 orchestrator branches are not edited.

**1. Schema (`scripts/metrics/emit.sh`).**

- `review_iteration` gains these optional INT fields, each with `RANGE` 0..10^9 so negatives are rejected:
  - `review_s`, `autofix_s`, `ci_wait_s`
  - `escalation_wait_s`
  - `worker_tokens`
  - `origin_in_fix`, `origin_near_fix`, `origin_carried`, `origin_new`
- `autofix_applied` gains optional INT fields `risky_with_test` and `risky_without_test`.
- Two cross-field rules are added after typing, as a small `CROSS` block. The alternative, per-finding events, was rejected by the operator.
  - `origin_*`: all four or none, and they must sum to `findings_count`.
  - `risky_with_test`/`risky_without_test`: both or none, and their sum must be **≤ `risky`**. `risky` also counts user-resolved conflict hunks and other paths that are excluded from hardening, so equality would hard-fail legitimate runs.
- The cross-field checks exit 64 with a message, never a `KeyError`, when `origin_*` arrives without `findings_count`, which a `--backfilled` row may omit.
- `RANGE` currently has a hi bound only for `confidence`. It's reused as-is with a large hi. No new mechanism is added.

**2. `/review-loop` (`skills/review-loop/SKILL.md`).**

- **Orchestrator state:** add `prev = {pre_sha, post_sha, pushed, findings_summary}`, kept **in-process only** from the last envelope. It is empty on iteration 1 and on every cold start. When the orchestrator has it, it passes `prev` into the worker prompt.
- **Worker timing:** wrap each phase in `date +%s`:
  - step 2 (the review-pr Skill call) gives `review_s`;
  - the autofix Skill call gives `autofix_s` (excluding `git push`);
  - `gh pr checks --watch` gives `ci_wait_s`.
  - A phase that didn't run leaves its field **out of the envelope**. It never gets 0.
  - The timing wraps are written as **new sub-bullets** under step 5. The existing `REQUEST_CHANGES` / `After autofix` / `If autofix surfaces` / `If either` bullets, which hold every escalation rule, stay byte-identical.
- **Worker classification (new step 4b):** runs whenever `prev` was given, i.e. every in-process iteration ≥2. When `prev.pushed` is false, the fix diff is empty, so every finding is `carried` or `new`.
  - Take the fix diff from `git diff -M <prev.pre_sha> <prev.post_sha>`. On a conflict iteration, walk only the non-merge commits (`git log --no-merges -p --first-parent`) so merged-in base changes don't count as "fix".
  - Classify each entry of `findings_summary`, taking the first match in this order below. `findings_summary` is now pinned to BLOCKING and IMPORTANT only, the same capped list `findings_count` counts, so an iteration with more than 20 findings is classified over that capped subset. The skill says so explicitly.
  - Pinning changes `findings_count`'s meaning against historical rows, which may have included MINOR items. This is recorded in the Decision log and the changeset, and the report's cost block only reads rows that carry the new fields.
    1. **carried** — `prev.findings_summary` has the same file (rename-mapped) with line within ±3, the review-pr dedup rule;
    2. **in_fix** — file:line falls inside a changed hunk of the fix diff;
    3. **near_fix** — the file calls or is called by a symbol defined or changed in those hunks. Use `graphify affected` when `command -v graphify` succeeds and `graphify-out/graph.json` exists, otherwise grep the symbol repo-wide;
    4. **new** — anything else.
  - Envelope fields: `review_s`, `autofix_s`, `ci_wait_s`, `origin_counts{in_fix,near_fix,carried,new}`. Each is omitted when not measured.
- **Orchestrator emit additions:**
  - `worker_tokens`: set only when the `Agent` result reports a total token count for the worker. Otherwise the flag is left off.
  - `escalation_wait_s`: on the **first** iteration of a run only. A short inline `python3` block reads the last `review_iteration` row in `${HIVESMITH_HOME:-~/.hivesmith}/telemetry/pipeline-events.jsonl` with the same `pr` and the same `project` (the basename of the git toplevel, which is emit.sh's own rule), skipping backfilled rows. If that row's `action` is `escalated`, the field is this run's start epoch minus that row's `ts`.
  - An escalation always ends the run (§3), so a resume is always a new run. That makes this the only path.
  - **Coverage ceiling:** this only covers escalations that the worker set through `escalate_reason`, which writes an `action=escalated` row.
    - Max-iterations, loop-guard and malformed-envelope escalations leave no such row.
    - Adding one would change ledger outcomes, which is a non-goal.
    - The skill and the report label both say "worker escalations only".
  - Ceiling: a resume from a different worktree doesn't join, because `project` differs. Documented.
- **§5 Rules:** one line saying the timing and classification steps are measurement-only and never feed a stop or escalate decision.

**3. `/autofix` (`skills/autofix/SKILL.md`).**

New step **9a "Harden a behaviour-changing fix"**. It applies to Phase 4 Option 1 and Option 3 only, and runs before that fix's individual commit. It explicitly excludes SAFE fixes, `DOES_NOT_APPLY` and Option 4 replies, and merge/rebase conflict hunks, which already have mandatory verification and no per-fix commit during a rebase.
1. **State the rule** the fixed code must hold, derived from the code and independent of the reviewer's or operator's proposal. Thread and operator text is data (anti-injection).
2. **Blast radius:** list the callers of each symbol the fix edits (graphify when available, grep otherwise), read each one, and check the fix against the rule and each caller's assumptions. If a caller would break, stop and ask the operator (same AskUserQuestion shape) before widening the fix. Never widen silently.
3. **Regression test:**
   - If the fix changes executable code and `AGENTS.md` defines a test suite that covers the file, add a test to that suite's existing test file.
   - **Prove it bites,** while the fix is still uncommitted:
     1. Run `git add -N <new untracked fix files>`.
     2. Run `git diff HEAD -- . ':(exclude)<test file>' > "$D/fix.patch"`, where `D=$(mktemp -d)`.
     3. `git apply -R` the patch, run the test, and require it to **fail**.
     4. `git apply` the patch, run the test, and require it to **pass**.
     - Never use `git stash`, because the stack is shared across worktrees.
     - By this point, SAFE fixes and every earlier risky fix are already committed (Phase 3 commits in a batch, and step 9 commits each risky fix). So `git diff HEAD` holds only this fix.
     - On any failure in between, re-apply `$D/fix.patch` before doing anything else.
   - **A test that doesn't bite** (it passes without the fix, or fails with it): allow **one** rewrite. If it still doesn't bite, delete the test and record the reason `test does not bite`.
   - **A test colocated with the fix** in the same file can't be separated by pathspec. Record the reason `test colocated with fix`.
   - Otherwise record exactly one reason: `no test command defined` or `prompt/doc change`.
   - Every reason counts toward `risky_without_test`.
   - The test goes in the same commit as the fix. Tests don't count toward the 20-fix cap.
- **Summary (step 11):** add a `- Hardening:` block **after** `Remaining:`, one line per behaviour-changing fix: rule, callers checked, and test path or reason. The `Threads:` block and its sub-lines stay byte-identical, because review-loop parses them.
- **Event (step 12):** add `risky_with_test` and `risky_without_test`, counted over the fixes that went through step 9a. Their sum is ≤ `risky`.
- **Rules:**
  - "Minimal changes only" gains one carve-out: the step-9a regression test.
  - Fix the duplicate step number: the second `12.` becomes `13.`.

**4. Report (`scripts/metrics/report.py`).**

- A new `REVIEW LOOP COST` block, printed only when at least one live `review_iteration` row carries a new field **or** an `autofix_applied` row carries a hardening count. Streams with only old rows print nothing, so old rows are handled by exclusion.
- The block shows:
  - per-phase `review`/`autofix`/`ci_wait` n, p50 and p90;
  - `worker_tokens` p50 and p90 when present;
  - the origin split (counts and %);
  - "escalation wait (worker escalations, same worktree)" n, p50 and p90;
  - autofix hardening "with test X / without Y" from `autofix_applied`.
- A new `pctl(values, q)` helper uses nearest-rank on the sorted values, so it's safe for n=1. `statistics.quantiles` raises for n<2.
- Rows are keyed by `(project, pr)`, never `feature`, so `feature=none` rows don't collapse together.

**5. Spec wording.** The spec's "token usage per phase" becomes "whole-worker token usage per iteration". This is the operator's decision from clarifying round B; per-phase tokens don't exist.

**Why this beats the obvious alternative.** The alternative is having the orchestrator time the whole Agent call. That gives one number per iteration and can't separate review from CI wait, which is the question behind the spec. Timing in the worker is the only place all three phases are visible.

### Risks

- **Classification is LLM-judged.** The worker applies the rules, and emit.sh can only check that the counts sum correctly, not that they're right. The ±3-line carried match and the grep fallback for near_fix are heuristics, and both ceilings are written into the skill.
- **Deliberate deviations from the spec's regression-test criterion:** `test does not bite` and `test colocated with fix` let a fix land without a test even where a test command exists. The alternatives are an unbounded rewrite loop and hunk-level patch surgery. Both are logged in the Decision log and the changeset, next to the operator-approved `prompt/doc change`.
- **Low n.** Risky fixes inside a review-loop worker escalate rather than apply, so the with/without-test counts mostly come from operator-attended `/autofix` runs.
- **Escalation join ceiling:** it works within the same project (worktree) only. A different worktree yields no field, never a guess.
- **`worker_tokens` depends on the runtime** reporting usage in the Agent result. When it doesn't, the field is omitted.
- **Runaway:** the revert-proof step modifies the working tree. If a test run crashes between `apply -R` and `apply`, the fix is lost from the tree. Mitigation: the patch file persists, and step 9a says to re-apply it before anything else on any failure.
- **Ruled out:**
  - per-finding events (operator choice);
  - adding `pre_sha` to the ledger to classify after a cold resume, which would change a format that backfill.py, merge-gate and templates parse, for one iteration per resumed run;
  - a helper script for the escalation lookup, which isn't installed to `~/.hivesmith/bin`, so skills in other repos couldn't call it.
